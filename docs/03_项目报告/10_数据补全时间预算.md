# 充 2000 积分后：数据补全的时间预算（2026-10-05 实测）

> **结论先说**：下载 **约 1.9 小时**，加清洗与重跑检验，**总计约 3.5 小时**。
> 瓶颈不是本机性能，是 Tushare 的频次限制。

---

## 一、实测基础数据

| 项目 | 实测值 |
|---|---|
| A 股数量 | 5,593 只 |
| 数据区间 | 2015-12-01 ~ 2026-10-02 |
| 交易日数 | 约 2,829 天 |
| **Tushare API 往返延迟** | **89 ms**（8 次采样中位 100ms） |
| 2000 积分档频次上限 | 200 次/分钟 = 3.33 次/秒 |
| 每日调用上限 | 10 万次/接口 |

**关键判断：本机网络延迟只有 89ms，8 线程并发后网络耗时仅 4 分钟。
真正的瓶颈是 Tushare 的 200 次/分钟限频。**

## 二、要拉多少数据

**关键点：本机已有 16.4M 条日线，只补「缺失」和「污染」，不重复拉已有内容。**

| 任务 | 拉取方式 | 调用次数 | 返回行数 | 优先级 |
|---|---|---|---|---|
| **`adj_factor` 复权因子** | 逐只 × 5,593 | 5,593 | 15,822,597 | ★★★ |
| **`index_member_all` 行业成分** | 逐只 × 5,593 | 5,593 | 212,534 | ★★★ |
| **`daily_basic` 每日 PE/PB** | 逐只 × 5,593 | 5,593 | 15,822,597 | ★★ |
| `stock_basic`（退市股） | 1 次 | 1 | 全量 | ★★ |
| `index_classify` 申万 L1/L2 | 2 次 | 2 | 全量 | ★★ |
| **合计** | | **22,374** | **约 3,200 万行** | |

**策略说明**：采用「逐只拉取」而非「按日期拉取」。
- 逐只：5,593 次/接口，每次返回该股全历史（2,829 行 < 单次上限 6,000）
- 按日期：需 2,638 次/接口，但按日期拉全市场时单次返回会被 6,000 行上限截断
- **逐只更省且更简单**

**每日上限检查**：单接口最大 5,593 次 = 上限的 **5.6%** → **单日可完成**。

## 五、最快路径：分阶段跑

不必一次跑完，可以分两个阶段：

### 阶段一：只修最严重的问题（约 1 小时）

```bash
# 只拉复权因子（5,593 次调用 ≈ 28 分钟）+ 行业分类（2 次）
uv run python scripts/fetch_tushare_supplement.py --adj-factor-only
```

修完这两项，解决：
- ✅ 2.33pp 年化偏差（复权）
- ✅ 37.2% 行业缺失（行业分类）

**这是 90% 的数据缺陷。**

### 阶段二：补充其余（约 1.5 小时）

```bash
uv run python scripts/fetch_tushare_supplement.py --all
```

补 `daily_basic`（每日 PE/PB）+ 退市股。

## 七、可能的意外

| 风险 | 影响 | 应对 |
|---|---|---|
| **复权因子拉不全**（接口分页/截断） | 部分股票仍污染 | 检查返回行数是否 = 2,829/只 |
| **触发限流惩罚** | 被临时封禁 | 脚本已留 10% 余量 + 遇限流自动 sleep 20s |
| **`index_member_all` 无权限** | 行业仍缺 37.2% | 改用本机 boards 547 板块（免费） |
| **网络中断** | 进度丢失 | 脚本每 500 只打印一次进度，可断点续跑 |
| **退市股代码不在本机** | 需重新拉它们的行情 | 额外 1,247 只 × 2,829 天 |

**最可能出问题的是第 1 项**——Tushare 的复权因子接口有时会分页，
买完积分后第一件事应该是**先拉 1 只股票验证行数**：

```bash
uv run python scripts/fetch_tushare_supplement.py --limit 1 --adj-factor-only
```

确认返回约 2,829 行再跑全量。
